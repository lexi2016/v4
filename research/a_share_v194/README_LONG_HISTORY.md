# V194 long-history runner

This folder adds an A-share-only continuation runner around the existing V194 model and report kernels. It does not change the accepted short R1 batch or any legacy `model194.py`, `run194.py`, `report194.py`, or data module.

## Runtime contract

`long_run194.py <execution-contract.json>` accepts only registered `canary`, `oof`, `refit`, or `predict` stages. It appends lifecycle events through the existing `registry_bridge.py` and reuses the existing `run194.py`, `model194.py`, and `report194.py` data/model/evaluation kernels. The OOF stage calls the same fold and reporting kernels through a narrow parallel coordinator because the legacy coordinator is serial. No second model or registry is introduced.

Before importing `run194` or fitting, the runner sets and reads back the native math-library thread variables in `long_training_adapter.py`. The reusable first-fold model canary, refit, and prediction stages run with one process. OOF folds may run in spawned processes using `runtime_budget.fit_workers`; after OOF inputs load, the successful canary's bound peak RSS and current available memory cap worker count, and `processes × threads_per_process` must stay within the configured twelve-thread maximum. Each worker sets its native limits before importing the legacy model kernel. A completed fold is sealed in a unique `_incomplete/<execution_id>/` directory and atomically promoted to its canonical cache path; existing sealed folds are verified and reused, and final aggregation follows frozen split order. The model runner writes PID, start, periodic heartbeat, checkpoint, and terminal resource receipts under `_runtime/<execution_id>/<stage>/`, so multiple registered stages can share an output root without overwriting receipts.

On macOS, `runtime_snapshot()` first uses `SC_AVPHYS_PAGES` when the platform exposes it. When that `sysconf` key is unavailable, it reads the reported page size and `Pages free` plus `Pages inactive` from `/usr/bin/vm_stat`; speculative and purgeable pages are omitted, and a malformed, failed, zero, or above-physical estimate remains unmeasurable so the existing serial fallback or memory guard applies. `mac_parallel_canary194.py` is a separately registered, research-only CPU runtime check: it accepts a frozen config path plus expected SHA, verifies its separate generated-workload input path and SHA, binds the output path in that config, and then runs deterministic numeric shards through the same spawned-process and native-thread initializer pattern. The real model-worker cap is bound to the successful prior fit-canary receipt's `runtime.process_peak_rss_bytes` and receipt SHA. The new receipt reports requested/selected/actual workers and observed thread pools. Apple Accelerate is not supported by the installed threadpoolctl: for this backend the CPU canary sets and reads back Apple's thread-local BLAS mode, then reads only its own worker task's Mach thread CPU counters before and after each unchanged matrix multiplication. Positive CPU deltas keyed by stable thread IDs count observed participants, including the calling thread; the receipt preserves per-call IDs and CPU deltas. Single-thread mode is explicit; the multithread mode is automatic and its readback is never treated as a thread count. Exact requested counts still must be observed, and missing/invalid observations fail closed. This call-boundary observation is not a scheduler concurrency or transient-thread guarantee. The separate v2 `TRAINER_CONTROL_PATH` protocol calls the existing `configure_native_thread_budget` in each spawned initializer before NumPy import and disables the canary SDK setter. It first observes the previously unverified trainer-only 1×1 path, then attempts 2/4/8/12 processes with exactly one observed CPU participant per worker under the same guard. Its mode getter is read-only; no configured limit or mode is counted as actual threads. This protocol does not repeat or replace the R2 SDK calibration or turn the original exact 3/6-thread matrix into PASS. The final v4 `CPU_ONLY` protocol reads only its generated workload and the SHA-bound R2 numeric RSS calibration, applies the unchanged selector with a 50% reserve, and raises the guard peak if the live numeric RSS is higher. It never reads model-RSS receipts, creates model objects, fits or evaluates a model, or calculates a model resource preview. Its only success label is `CPU_PARALLEL_PASS_MODEL_NOT_RUN`, with explicit zero model objects/fits and `model_evaluation=NOT_RUN`. Original R2/R3 stops and abandoned R4 source snapshots remain preserved. It does not load V194 inputs, fit a model, create predictions, labels, or OOF results.

Every model stage requires `input_manifest_path`, `input_manifest_sha256`, `independent_input_review: {path, sha256}`, and an explicit `frozen_universe` binding in its run config. For the current reviewed child manifest, the adapter accepts only the exact R2 bounded-research receipt → R1 fixed-pool/candidate/truth component → R2 metadata-child/long-parent manifest chain. It verifies each receipt and manifest SHA, the child coverage and data-dictionary paths/SHAs/coverage row count against the R2 result, and the separate source ancestry from the long input-build contract to its short-R1 source manifest. It also verifies the sorted unique 5,533-code list and normalized market-code format, 11 technical features, three source-state fields, frozen label/formula identity, and unchanged model-input files/date policy across the parent-child edge. This is a bounded research-input PASS only: `whole_input_status=CANNOT_CONFIRM`, historical/source vintage and calendar parity remain unverified, the A194 passport remains unissued, and the maximum claim remains `DIRECTION_ONLY`. A narrow V2 compatibility validator checks those unchanged research-only statuses and exact feature/label/pool bindings without editing the manifest or setting legacy `semantic_ready`/training flags. The frozen model remains C=1.0 L2 Logistic Regression, `lbfgs`, seed 194, `max_iter=1000`, `tol=1e-8`, with a train-fold-only scaler; each fold fits the baseline and V194 arms once. For OOF the runner additionally requires a successful `fit_canary_runtime: {path, sha256}` terminal receipt. The canary must record exactly two completed real fits for the reusable first fold and zero synthetic fits. Its identity binds the input manifest/review and 5,533-code list, native-thread setting, legacy model/report/runner code hashes, long runner/adapter hashes, model-config hash, full frozen-plan hash, and first-fold ID/hash. OOF checks the runtime/input/code fields before reading the canary and compares the exact model/frozen-plan/first-fold identity after loading its frozen plan but before spawning workers. A missing or mismatched input review or canary fails before OOF fit workers start.

Before any canary, OOF, or refit fit, the runner also binds the run config's `DATE_POLICY.json` path and SHA to the exact `files.date_policy` entry in the reviewed input manifest. It recomputes the frozen eligible-date split and verifies the policy's initial training dates, OOF date folds, OOF dates, diagnostic exclusions, and Top50 cutoff. For the reviewed bounded-input schema, a narrow long-run adapter builds the same `RUN_FREEZE` plan while grouping truth denominators and train-label availability/classes in passes over the input rows; it avoids rescanning the full truth table once per eligible date. A small fixture compares its complete five-part return value with the unchanged `run194.prepare()` path and checks matching denominator-drift and one-class errors. The guarded plan is checked before a fit; OOF rechecks the loaded plan before worker spawn. Prediction-only stages do not build a training plan.

After a registered `RUN_STARTED`, all Python `BaseException` exits, including `KeyboardInterrupt` and `SystemExit`, attempt to append the official failure `TERMINAL` event and then re-raise the original exception. When the heartbeat context started, it also records the local failed terminal receipt.

## Implementation verification

After the registered OOF and report-recovery stages, the local report output includes `LONG_DAILY_MODEL_COUNTS.csv` (one row per frozen target date) and `OOF_DAILY_SELECTION_COMPARISON.csv` (one row per OOF date). In `LONG_DAILY_MODEL_COUNTS.csv`, the baseline/V194 `common`, `new`, and `lost` columns count intersections of selected names; they are not counts of true target hits. Use `OOF_DAILY_SELECTION_COMPARISON.csv` for the primary daily hit comparison: its separate `*_hits` columns contain actual Top100 target hits, with `selection_slots` kept separate from the 100-positive denominator. It contains 473 OOF-date aggregate rows and no stock codes. On these dates, the technical L2 baseline and V194 record 2,046 and 2,052 hits over 23,650 selection slots each; 2,029 hits are common, with 23 V194-only and 17 baseline-only hits. The paired mean is 0.012685 extra hits per day and its frozen 95% interval is [-0.025370, 0.040169], so the predeclared breakthrough gate fails and the result remains `NO_BREAKTHROUGH` / `DIRECTION_ONLY`. The summary keeps training-only, diagnostic, and excluded dates null with their reason rather than treating them as zero selections. It also carries raw-union and model-candidate source-state counts with separate denominators for fupan, stage7, and research; `unknown` is never inferred as confirmed absence. `LONG_SOURCE_COVERAGE_BY_YEAR.json` aggregates the explicit row-count schema by year and source scope. `RAW_FORMULA_NATURAL.csv` means the raw formula's own `tech_192==1` membership, even if an unrelated technical flag is unknown; the model view separately requires all eleven technical flags. The 5,533 codes are the fixed research universe and do not establish historical all-A-share membership. Historical source publication time/vintage, official-calendar parity, the A194 passport, sealed-forward performance, and execution-cost-adjusted alpha remain `CANNOT_CONFIRM`.

`test_long_run194.py` checks the native-thread cap, canary/RSS worker selection and fit identity, registered `BaseException` terminal handling, exact-universe and independent-manifest PASS gates, R2 metadata-file and source-ancestry bindings, rejection of the full parent as runtime child, date-policy path/hash/split binding, bounded-plan parity and matching validation errors against the legacy prepare path, source coverage/audit semantics, summary-only output behavior, and durable local PID/checkpoint/terminal receipts. These are runtime-unit checks only; they do not read market rows, run the builder or fit canary, fit a model, produce OOF results, or certify the input passport.
