# V4优化提案：先保证一条真实业务链，再减少耦合与重复工作

性质：待Chat审查的方案，未实施。优先级是建议顺序，不是新的V5验收阶段；V5仍按原01—18/P0—P5。

## 目标与约束

用户要可持续使用的股票研究系统：真实采集→原算法→保存→普通页面显示股票及理由。必须保留V4、来源身份/时间/资格及研究安全字段；不交易。研发在当前会话完成；Mac仅负责必要落地、独立验收、部署。当前请求只授权梳理与GitHub交接，不以此恢复部署。

系统慢与助手执行慢分开：本包发现的同步调用、重复读取和长链耦合是静态审查对象；没有延迟profiling，不能声称已测得性能瓶颈。此前大量交接未转成页面发布属于执行安排问题，不应通过删除业务门禁解决。

## 方案一：先固定唯一可部署组合（最高优先）

- 输入：Mac活动source/binding/配置/前端身份的已有回执，以及各候选固定提交。当前只有历史源码和候选，不能假定GitHub某HEAD等于Mac全部现役。
- 产物：一张每文件before/after/source-owner表，明确“保留现役、接入既有补丁、需要新修复、暂不迁移”。同功能多候选做语义合并矩阵，禁止按提交日期整文件覆盖。
- 从经理链开始：旧R3、四功能R2与10月10日返回候选必须逐项核查。8c8e35、fa97ac、c8935da是不同候选线，POST后直接消费还是canonical GET、identity规范化范围等存在合同差异；先比较响应是否同一规范产品，再由Chat明确选择，不能拼接两种刷新行为。以DELIVERY_PIPELINE_REVIEW的路由差异为输入，保留US owner生产/读回、计划日期与身份、诊断覆盖等各自修复。
- 验收：必要闭包存在且SHA正确；候选不可变；依赖和回滚可追；运行版本能从实际进程/API/静态manifest核对。
- 停止条件：活动字节未取得时，不给可执行整树覆盖命令；仍可完成静态差异方案。

## 方案二：完成一条最小真实发布链，而不是再扩平台

- 公告：使用已存在且身份成立的本机结果，沿原consumer→原manager保存→普通API→普通页面。已有392决策的数字来自本机既有回执，本轮不重新读取原件，也不算本轮新增采集/业务验收。
- 每个结果包含原evidence run、经理run、目标日/来源日/cutoff、产物SHA。公告run与经理run不是同一个概念；“同run读回”指读回所声明的那一份已提交经理计划，内部引用的各来源身份完整。
- 发布路径：既定候选启动→必要测试及真实API读回→运行源码/静态资源身份→单窗口切换→普通页核对；失败回到已知旧版本且保留失败证据。
- 内置浏览器视觉验收单独登记，不能用Chrome替代用户指定IAB；IAB不可用不自动阻止可独立完成的已授权后端步骤，但不签页面视觉通过。
- 验收：股票/理由/来源/资格/缺口可见；刷新与重新请求不生成另一个结果；旧结果明确过期。健康lane保留展示。
- 局部公告发布≠三策略首批退出≠18模块完成。

## 方案四：普通读取和长任务解耦，先测再决定拆分

- 源码显示部分“独立子进程”通过RPC回到API owner计算；这不是完整计算进程隔离。先核调用与资源占用，再选择最小变更。
- 短期保留现有writer/锁，普通GET只读已提交产物；长任务返回既有job/run状态，重复提交幂等。不要边读页面边重采数据。
- 如确有线程占用：将重计算保留在唯一producer中，API只返回已提交引用；保持请求合同与同run终态读回。先做经理链，不连带重构Stage。
- 建议测量（本轮NOT_RUN）：健康/普通GET、生成POST、源验证、计算、序列化、持久化、读回分别记录耗时与输入规模；注明冷/热、并发数、机器/依赖/提交。
- 不预设未经测量的提速百分比或SLA。用户价值是生成时普通页面仍可读、坏lane不拖垮健康lane。
- 缓存只能绑定代码/配置/输入/target/cutoff身份；不得用缓存绕过tamper或历史PIT校验。

## 方案五：复用调度和恢复，消除重复采集与错误重试

- 既有stage锁、attempt预算、deadline与节点receipt保留，不建第二调度器争抢同owner。
- 每次失败区分输入未到、永久合同拒绝、可重试网络、执行中未知副作用。未知副作用先查询原run，不立即再提交。
- latest_attempt与latest_success分开：今天失败可展示旧成功，但日期/过期状态明确；不可变正式池不被缺输入占位污染。
- 断线恢复先读持久化run和实际进程身份。连接通知、端口探测权限错误、进程退出是三种事实，不能互相替代。
- 验收：重复触发不重复生产；中断后恢复同attempt或明确新attempt；下一适用日更新；源变化派生新identity；故障注入不丢已有成功。

## 方案六：逐步降低维护成本（主链稳定后）

1. globals/parts转发逐处改显式依赖：先一处试点，原输入输出回放相等后再扩；不一次重写全库。
2. 公共合同用已有类型和校验函数统一表达日期、单位、status、引用；不要新增与旧合同不兼容的“万能schema”。
3. 大计划的必要证据以原有有界存储机制保留引用/内容；历史大文件缺陷先核现有修复，禁止无限放大读取上限、删权威字段或静默截断。
4. 测试分层：单元/合成、固定原件回放、真实采集、Mac部署、IAB视觉、自然接续分别登记。相同输入代码不变时复用证据；发生变化只重验依赖范围，最终固定候选再跑聚合门禁。
5. 建议长期补“代码→运行→产物→页面”的版本索引，优先复用已有manifest和ledger，不新建复杂平台。
